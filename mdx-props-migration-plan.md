# MDX + PropsTable Migration Plan

## Goal

Get `<InterfaceTable name="BreadcrumbsProps" />` rendering in `breadcrumbs.mdx` via real MDX compilation, using `propsRegistry` data generated by react-docgen-typescript (replacing Documentalist's TypescriptPlugin). Scoped POC: only `breadcrumbs.mdx` renders via the new path; all other pages continue using the existing Documentalist pipeline unchanged.

### Success Criteria
- `pnpm compile` passes
- `pnpm lint` passes
- `pnpm dev:docs` renders the breadcrumbs page with a working props table powered by `propsRegistry`
- All other doc pages continue working via Documentalist

---

## Background: Current Architecture

### How docs pages render today

```
.mdx source files (e.g. breadcrumbs.mdx)
  |
  v
Documentalist (compile-docs-data.mjs)
  - MarkdownPlugin: converts markdown to HTML, extracts @tags
  - TypescriptPlugin: extracts JSDoc from .tsx files
  - Output: src/generated/docs.json
  |
  v
docs-app/src/index.tsx
  - imports docsData from @blueprintjs/docs-data (the JSON)
  - creates tagRenderers: { interface: TypescriptExample, reactExample: ..., ... }
  - passes both to <BlueprintDocs> -> <Documentation>
  |
  v
Documentation component (docs-theme)
  - creates DocumentationContext (getDocsData, renderBlock, renderType)
  - routes pages via hash: activePageId = routeToPage[location.hash]
  - renders <Page page={pages[activePageId]} tagRenderers={...} />
  |
  v
Page component (docs-theme/src/components/page.tsx)
  - calls renderBlock(page, tagRenderers, Classes.TEXT_LARGE)
  |
  v
renderBlock() (docs-theme/src/components/block.tsx)
  - iterates block.contents[]
  - strings -> dangerouslySetInnerHTML (pre-rendered HTML from markdown)
  - Tag objects -> createElement(tagRenderers[tag], props)
  |
  v
TypescriptExample (docs-theme/src/tags/typescript.tsx)
  - handles "interface" tags
  - looks up docsData.typescript["BreadcrumbsProps"]
  - renders <InterfaceTable data={tsInterfaceData} />
```

## Implementation Plan

### Dependency flow (no circular deps)
```
docs-app  -->  docs-data   (imports propsRegistry)
docs-app  -->  docs-theme  (imports PropsTable, Documentation)
docs-data -->  docs-theme  (existing, unchanged)
```
PropsTable in docs-theme defines its own prop types (structurally compatible with PropsInfo from docs-data but no import). The bridge component in docs-app does the propsRegistry name lookup.

### Step 1: Add @mdx-js dependencies to docs-app

**File:** `packages/docs-app/package.json`

Add:
- `@mdx-js/loader` (~3.x) — webpack loader for .mdx files
- `@mdx-js/react` (~3.x) — MDXProvider for component injection at runtime

Run `pnpm install` after.

### Step 2: Configure webpack for MDX compilation

**File:** `packages/docs-app/webpack.config.mjs`

Add .mdx rule to `module.rules`:
```js
{
    test: /\.mdx$/,
    use: [
        {
            loader: "@mdx-js/loader",
            options: {
                providerImportSource: "@mdx-js/react",
            },
        },
    ],
}
```

Add `.mdx` to `resolve.extensions` (merge with baseConfig).

@mdx-js/loader v3 outputs ESM which webpack 5 handles natively.

### Step 3: Add TypeScript declaration for .mdx imports

**File (new):** `packages/docs-app/src/typings/mdx.d.ts`

```ts
declare module "*.mdx" {
    import type { ComponentType } from "react";
    const MDXComponent: ComponentType;
    export default MDXComponent;
}
```

### Step 4: Create PropsTable component in docs-theme

**File (new):** `packages/docs-theme/src/components/propsTable.tsx`

A new component that renders interface props using the new data shape from react-docgen-typescript. This is the eventual replacement for the Documentalist-based InterfaceTable.

**Prop types** (defined locally to avoid docs-data import):
```ts
interface PropsTableEntry {
    name: string;
    type: string;
    required: boolean;
    defaultValue: string | null;
    description: string;
    deprecated: boolean | string;
    internal: boolean;
    parentName: string | null;
}

interface PropsTableProps {
    name: string;
    description?: string;
    filePath?: string;
    props: PropsTableEntry[];
}
```

**Rendering approach:**
- Uses `ModifierTable` (from `../modifierTable`) for the table shell — same as existing InterfaceTable
- Each prop rendered as a `<tr>` row with:
  - Name column: `<code>{name}</code>` with CSS classes `docs-prop-name`, `docs-prop-is-required`, `docs-prop-is-deprecated`
  - Details column: type (`<code><strong>`)  + default value (`<em>`) + description + tags (Required/Deprecated/Inherited)
- Reuses `DeprecatedTag` from `./typescript/deprecatedTag`
- Filters out props where `internal === true`
- Same CSS classes as existing InterfaceTable (`docs-prop-name`, `docs-prop-details`, `docs-prop-type`, `docs-prop-description`, `docs-prop-tags`, etc.) so styling from `_props.scss` applies automatically
- Does NOT depend on `DocumentationContext` or `@documentalist/client`
- Type strings rendered as plain `<code>` text (no linkification for this POC — can be added later)
- Description rendered as text (react-docgen-typescript outputs plain text descriptions, not HTML)

**File:** `packages/docs-theme/src/index.ts` — add `export * from "./components/propsTable";`

### Step 5: Create MDX bridge components in docs-app

**File (new):** `packages/docs-app/src/mdx/mdxComponents.tsx`

This file creates the component map provided to MDXProvider. It bridges the gap between what the MDX file expects (simple `name` prop) and the actual data/component implementations.

Three components:

1. **`InterfaceTable`** — accepts `{ name: string }`, looks up `propsRegistry[name]` from `@blueprintjs/docs-data`, renders `<PropsTable>` from `@blueprintjs/docs-theme`
2. **`ReactCodeExample`** — accepts `{ name: string }`, looks up `reactExamples[name]` (from `../tags/reactExamples`), calls `example.render({ id: name })`
3. **`ReactExample`** — same as ReactCodeExample but also renders the "View source on GitHub" `<AnchorButton>` link (mirrors behavior of `ReactExampleTagRenderer.render`)

Exports a single `mdxComponents` object for use with `<MDXProvider components={mdxComponents}>`.

### Step 6: Update breadcrumbs.mdx to pure JSX syntax

**File:** `packages/core/src/components/breadcrumbs/breadcrumbs.mdx`

Convert all Documentalist `@tag` syntax to JSX:

| Before | After |
|--------|-------|
| `@reactCodeExample BreadcrumbsBasicExample` | `<ReactCodeExample name="BreadcrumbsBasicExample" />` |
| `@reactCodeExample BreadcrumbsOverflowExample` | `<ReactCodeExample name="BreadcrumbsOverflowExample" />` |

### Step 7: Add page override mechanism to Documentation component

**File:** `packages/docs-theme/src/components/documentation.tsx`

Add one optional prop to `DocumentationProps`:
```ts
/**
 * Map of page IDs to React components that override the default Documentalist
 * page rendering. When activePageId matches a key, the component is rendered
 * instead of the Documentalist-based <Page>.
 */
pageComponents?: Record<string, React.ComponentType>;
```

In `render()`, around line 241 where `<Page>` is rendered inside `<main>`, add a conditional:
```tsx
const PageOverride = this.props.pageComponents?.[activePageId];
// inside <main>:
{PageOverride ? (
    <Suspense fallback={<Spinner />}>
        <div className="docs-page" data-page-id={activePageId}>
            {renderActions && <div className="docs-page-actions">{renderActions(pages[activePageId])}</div>}
            <PageOverride />
        </div>
    </Suspense>
) : (
    <Page
        page={pages[activePageId]!}
        renderActions={this.props.renderPageActions}
        tagRenderers={this.props.tagRenderers}
    />
)}
```

The wrapper `<div className="docs-page">` and `data-page-id` match what the existing `Page` component renders, preserving scroll/routing behavior.

### Step 8: Wire up MDX page in BlueprintDocs

**File:** `packages/docs-app/src/components/blueprintDocs.tsx`

1. Lazy-import the breadcrumbs MDX component:
   ```tsx
   const BreadcrumbsMdx = lazy(() => import("../../../../core/src/components/breadcrumbs/breadcrumbs.mdx"));
   ```

2. Create a wrapper that provides MDXProvider context:
   ```tsx
   import { MDXProvider } from "@mdx-js/react";
   import { mdxComponents } from "../mdx/mdxComponents";

   const BreadcrumbsPage = () => (
       <MDXProvider components={mdxComponents}>
           <div className="docs-section">
               <div className="bp5-running-text bp5-text-large">
                   <BreadcrumbsMdx />
               </div>
           </div>
       </MDXProvider>
   );
   ```

3. Pass to Documentation:
   ```tsx
   const pageComponents = {
       "breadcrumbs": BreadcrumbsPage,
   };

   <Documentation
       {...this.props}
       pageComponents={pageComponents}
       // ... existing props unchanged
   />
   ```

**Note on page ID:** The key in `pageComponents` must match `activePageId`. Based on how `compile-docs-data.mjs` builds the nav tree, the page reference for breadcrumbs is likely `"breadcrumbs"` (the leaf entry from nav.json, used as the key in `pages`). Verify at implementation time by checking `docs.json` or adding a `console.log(activePageId)` in Documentation.render().

## Risks & Considerations

1. **@mdx-js/loader v3 requires ESM** — webpack 5 should handle this, but if there are issues with the swc-loader pipeline, may need to fall back to @mdx-js v2 or add babel-loader for .mdx files specifically.

2. **Page ID verification** — the exact `activePageId` for breadcrumbs needs to be verified at implementation time. It's determined by Documentalist's page reference extraction from the nav tree. Most likely `"breadcrumbs"` but could be a full route path.

3. **Heading extraction for nav** — Documentalist's MarkdownPlugin extracts `#` headings for the nav tree. Since headings remain as markdown in the updated MDX, nav extraction should continue to work.

4. **`@ns` namespace interpolation** — Documentalist replaces `@ns` with the Blueprint CSS namespace (`bp5`). MDX compilation doesn't do this. The POC replaces literal `@ns` occurrences in breadcrumbs.mdx with `bp5`. A remark plugin could automate this for future migration.

5. **Description rendering** — react-docgen-typescript descriptions are plain text (with possible markdown like backtick code). The initial PropsTable renders these as text. Adding markdown rendering (e.g. via a lightweight markdown renderer) is a follow-up.

6. **Type linkification** — The existing InterfaceTable uses `renderType()` from DocumentationContext to linkify type names (e.g. clicking `Intent` opens the API browser). The new PropsTable renders types as plain code text. Linkification can be added later when more of the system is migrated.

7. **CSS styling** — PropsTable reuses the same CSS classes from `packages/docs-theme/src/styles/_props.scss` as the existing InterfaceTable, so it should look identical visually.

8. **Dual processing** — breadcrumbs.mdx will be processed by both Documentalist (for nav/routing) and @mdx-js/loader (for rendering). This is intentional and acceptable for the transition period. The Documentalist-rendered version of the page exists in `docs.json` but is never displayed because the `pageComponents` override takes priority.

9. **Future migration path** — Once this POC validates the approach, additional .mdx files can be converted one at a time by: (a) converting their `@tags` to JSX, (b) adding lazy imports in blueprintDocs.tsx, (c) adding entries to `pageComponents`. Eventually, Documentalist's TypescriptPlugin and the old `InterfaceTable`/`TypescriptExample` components can be removed entirely.
